================================================================================
KEY DESIGN DECISIONS
================================================================================

1. build_version = build_tick in history
   Why: PRIMARY KEY is (network_name, build_version). To avoid conflicts while
        keeping all historical data, we set build_version = build_tick.
   Benefit: Multiple build_ticks coexist in same table, each unique by PK.

2. network_version stores actual structural version
   Why: Phase C still increments networks_release.build_version structurally.
   Benefit: Can track both axes: time (build_tick) and structure (network_version).

3. Snapshot ALL networks
   Why: Old logic only inserted changed networks, causing sparse history.
   Benefit: Every network has rows for every build_tick, enabling trend calc.

4. Idempotent design
   Why: Reruns of the same build_tick should be safe.
   Benefit: Detect existing snapshots and skip redundant writes.

# X30.0 — Operation-Agnostic Discovery Audit

Investigation only, per the brief. No code changed. Traces the actual implementation of `operational_lineage.py`, `funding_topology.py`, `funding_mechanism.py`, `operation_identity.py`, `operations_summary.py`, and `discovery.html` (not reasoned abstractly) to determine whether Discovery's concepts are operation-agnostic or implicitly WATCHTOWER-specific.

## Roles — audited one at a time

| Role | Explicit or inferred? | WATCHTOWER-specific? | Could another operation omit it? |
|---|---|---|---|
| **Treasury** | Explicit for the confirmed set (`wt_confirmed_treasuries`), inferred structurally elsewhere (appears as `from_wallet` on a `TREASURY_TO_SUBPROV` edge, or `treasury_wallet` on a launch — `operational_lineage.py:81-94,107-111`). | No — "the funding root of a chain" is a genuinely general concept. But the *confirmation mechanism* (`wt_confirmed_treasuries`) is built for WATCHTOWER's specific treasury-vetting process; a different operation family would need its own root-confirmation logic, not necessarily this table. | Yes, trivially — any two-party operation (funder→creator direct) has a root, whatever you call it. |
| **Subprovider** | Inferred only — never a first-class confirmed set with its own table; derived purely from edge participation (`to_wallet` on `TREASURY_TO_SUBPROV`, or `from_wallet` on `SUBPROV_TO_CREATOR`, `operational_lineage.py:91-104`). | **Yes, heavily.** The name itself, the WSOL-wrap-close-shaped edge type it's derived from (`SUBPROV_TO_CREATOR`), and its supporting properties (`fan_out_count`, `funding_mechanisms` — both WSOL-wrap-close-flavored, `_node_properties`, `operational_lineage.py:248-262`) are WATCHTOWER's specific intermediate-funder pattern. | Yes — X29.7's own 2-hop `treasury_wallet` direct-to-creator case (`_find_direct_treasury_for_creator`, `operational_lineage.py:213-224`) is already a real, tested case of an operation with **no subprovider role at all**. |
| **Creator** | Explicit — `creator_wallet` on `wt_watchtower_launches`, or `to_wallet` on `SUBPROV_TO_CREATOR` (`operational_lineage.py:101-105,116-119`). | The *name* "Creator" (as in, "creates a token") is Pump.Fun/launch-specific — a non-launch operation (e.g. a pure trading-coordination ring) would have no equivalent role at all, not merely a renamed one. | Yes — any non-launch-producing operation family has no Creator role by definition, not an optional omission but a category mismatch. |
| **Provisioned wallet** (Category A, X29.10 vocabulary) | Explicit, from `wt_subprov_evidence` — a WATCHTOWER-specific evidence table keyed on `subprov`/`creator_wallet`/`funding_mechanism` columns that assume the wrap-close shape (X29.9/X29.11 findings). | **Yes, entirely.** The table schema itself only models one mechanism family. | Yes — an operation using, say, only `PLAIN_TRANSFER` funding would never populate this table at all (confirmed in X29.8: `wt_provisioning_edges` has no edge type that can represent a plain-transfer branch — "0% by construction"). |
| **Candidate wallet** | Explicit, `wt_candidate_websocket_watches` — a live-WS observation-lifecycle state (`state`, `close_reason`, `expires_at`), confirmed in X29.11 to reflect an *active* sibling-suppression decision, not a role. | **Yes.** This is WATCHTOWER's specific candidate-observation machinery (the CDC→subprov promotion path traced below), not a role at all — it's closer to a workflow status than an operational identity. | Yes trivially — "candidate" only exists because WATCHTOWER's detection pipeline needs a provisional pre-confirmation state; an operation detected by a different mechanism (e.g. a single deterministic rule with no WS-observation window) would have no analogous state. |
| **CDC** (Capital Distributor Candidate) | Explicit, `ws_cascade.py:59-60,3167-3297` — a threshold-triggered (`CDC_MIN_SOL`) pre-role watch state that **promotes to SUBPROV once a wrap-close is observed** (`ws_cascade.py:3290-3297`: "If the CDC performs a wrap-close, it is confirmed as a subprov"). | **Yes, completely.** CDC is not itself an operational role — it is WATCHTOWER's own detection-state machine's name for "large unconfirmed inbound recipient, watching to see what it becomes." It resolves *into* Subprovider (or nothing). | Not applicable as a role at all for another operation family — it's an artifact of *this* detection pipeline's staging, not a concept another operation could have or lack. |
| **Trader** | Found once, in `operator_model.py:135`, in prose only ("...provisioner but individual traders can be reused independently") — **no dedicated Trader table, column, or role constant exists anywhere in `src/ops/`.** `wt_trader_wallets` exists only in the separate hot DB (`flex_complete_database.db`, confirmed absent from `wt_ops_v2.db` in X29.11) and was never found populated for any of the 24 sibling wallets checked. | Ambiguous by omission — "Trader" is referenced as a concept but never implemented as a queryable Discovery role. It is aspirational vocabulary, not a working concept. | Not meaningfully answerable — there is no current mechanism to evaluate. |
| **Provisioner** | Not a distinct constant anywhere in `operational_lineage.py`/`funding_topology.py`/`funding_mechanism.py`. Used informally as a synonym for Subprovider in comments/labels (e.g. discovery.html:557 `'Sub-provisioner'`) and as a name fragment in several detection tables (`wt_sub_provisioners`, `wt_swarm_provisioners` — both hot-DB, both unexamined by any Discovery-facing module). | Same status as Subprovider — a naming variant, not a separate concept. | N/A — it's not distinct from Subprovider in the current architecture. |

**Summary**: of the 8 roles/states examined, exactly 3 (Treasury, Subprovider-as-intermediate-funder, Creator) are load-bearing in the actual lineage/topology code, and of those 3, only "root funder" (Treasury, generically) and "terminal recipient" (Creator, generically renamed) are truly operation-agnostic concepts. Subprovider is WATCHTOWER's wrap-close-shaped intermediate hop specifically. CDC and Candidate are detection-pipeline staging states, not operational roles at all — conflating them with roles would be a category error if repeated in a redesign. Trader is unimplemented vocabulary.

## Funding topology — is the hierarchy universal, optional, or WATCHTOWER-specific?

Traced directly in `funding_topology.py`: **the classifier is honestly built to be topology-shape-agnostic in principle** (`FAN_OUT`/`LINEAR`/`MULTI_LEVEL_FAN_OUT`/`MESH`/`UNKNOWN`, evaluated in most-specific-first order, never assuming a fixed depth) — this is a genuine strength, and matches X29.7's variable-depth `build_lineage()` design.

However, two of its four real branches are WATCHTOWER-specific in their *evidence source*, not their *concept*:
- `MULTI_LEVEL_FAN_OUT`'s detection reads `watchtower_events.SUBPROV_SESSION_OPENED_WS` payloads with `via='subprov_plain_xfer'` (`funding_topology.py:79-107`) — a WATCHTOWER-specific event-emission convention from `ws_cascade.py`. A different operation family emitting no such event would never trigger this branch even if a genuine multi-level structure existed on-chain.
- `MESH`'s detection reads `wt_active_subprov_sessions.treasury_wallet`/`subprov_wallet` overlap (`funding_topology.py:110-148`) — the same WATCHTOWER-specific session table. The module's own docstring admits this rule currently matches **zero** treasuries in the live corpus despite qualitative evidence (memory: `treasuries-fund-treasuries`) that Mesh does occur — i.e., the *concept* is general, but the *only implemented detector* for it is scoped to WATCHTOWER's session-tracking tables.

**Conclusion**: the topology vocabulary (Fan-Out/Linear/Multi-Level/Mesh) is itself a genuinely universal description of funding-graph shape — any operation family, regardless of its funder-role names, produces one of these four shapes. What is WATCHTOWER-specific is *which tables the classifier currently knows how to read* to detect them. A new operation family emitting its own distinct edge/session tables would not be automatically classified — the classifier would need new evidence-reading branches, not new topology categories. This is the correct kind of extension (add a data source, not a new topology type) but it does mean topology detection today is **not yet architecturally decoupled** from WATCHTOWER's specific table names — every `_table_exists`/column check in the module hardcodes `wt_provisioning_edges`, `wt_watchtower_launches`, `wt_active_subprov_sessions`, `watchtower_events`.

The `Treasury → Subprovider → Creator` chain itself (as opposed to the FAN_OUT/LINEAR/MESH vocabulary) is **not** asserted as universal anywhere in the topology code — `classify_topology_for_launch` explicitly handles the "treasury recorded but no subprov at all" case as a first-class `LINEAR` result (`funding_topology.py:227-230`), and `operational_lineage.py`'s `build_lineage()` already renders a real, tested 2-hop chain with no subprov node. The three-role chain is best described as **the dominant observed case for WATCHTOWER, not an architectural assumption** — the code does not fabricate a subprov node when none exists.

## Funding mechanisms — does a mechanism imply a role?

Traced directly in `funding_mechanism.py` and `operational_lineage.py`. The answer is **mixed — mostly no, with one real conflation**:

- `funding_mechanism.py` itself is clean: `classify_mechanisms_for_launch()` returns mechanism tags (`WSOL_WRAP_CLOSE`/`PLAIN_TRANSFER`/`SEEDED_ACCOUNT_CLOSE`/`MIXED`) with **no role logic anywhere in the module** — mechanism is computed purely from `wt_watchtower_launches.funding_mechanism` and `wt_provisioning_edges.funding_mechanism`, additively, never used to assign or infer a role. This module answers "how did capital move," full stop.
- **The one real conflation is upstream, in the detection code, not in this classifier**: `ws_cascade.py:3290-3297`'s own comment states it plainly — *"If the CDC performs a wrap-close, it is confirmed as a subprov"*. This is a direct mechanism→role inference: observing `WSOL_WRAP_CLOSE` behavior is literally the promotion criterion from the CDC watch-state into the Subprovider role. This is a real, working, and — per X29.9's confirmed 3/3 on-chain validation of the wrap-close pattern — currently *reliable* rule for WATCHTOWER. But it means the platform's actual role-assignment pipeline (as opposed to the read-only `operational_lineage.py`/`funding_mechanism.py` presentation modules) **does** let a mechanism observation directly become a role identity, for this one specific mechanism.
- `operational_lineage.py`'s own `_node_properties()` reinforces this indirectly: `funding_mechanisms` is a property attached only to `SUBPROVIDER`-role nodes (`operational_lineage.py:252-257`), never to Treasury or Creator — an artifact of the fact that `wt_watchtower_launches.funding_mechanism` is scoped per-launch to describe the subprov→creator hop specifically, not a deliberate mechanism-implies-role rule in this module, but it does mean the presentation layer inherits the same WSOL-wrap-close-centric framing.

**Answer to the brief's example question directly**: today, detecting `WSOL_WRAP_CLOSE` means both things at once, depending which layer you look at — in `funding_mechanism.py` (the read-only classifier) it means *only* "observed funding mechanism"; in `ws_cascade.py` (the live detection pipeline) it means "promote to Subprovider." These are not contradictory so much as **the mechanism-implies-role rule lives entirely in the detection pipeline, and the read-only classifiers correctly do not re-derive or repeat it** — but that also means the "role vs. mechanism" separation the brief is asking about only exists in the presentation layer, not in the system that actually assigns roles in the first place.

## Operation identity — what does it actually depend on?

Traced directly in `operation_identity.py`. Operation identity depends on exactly one thing: **confirmed treasury-to-treasury funding edges, time-ordered before the destination treasury's first launch** (`build_operations()`, `operation_identity.py:85-250`). It does **not** depend on:
- subprovider existence — an operation with zero subprov hops (direct treasury→creator) is still assignable to an operation via this resolver, since the resolver only ever looks at `wt_confirmed_treasuries`/`wt_treasury_funders`/`wt_watchtower_launches.treasury_wallet`, never touching subprov columns at all.
- sibling suppression — entirely absent from this module; sibling-suppression is a candidate-observation-layer concept (`wt_candidate_websocket_watches`), never referenced here.
- funding topology or funding mechanism — neither `funding_topology.py` nor `funding_mechanism.py` is imported by or referenced in `operation_identity.py`.
- behavioural evidence — not read at all.
- launch history is used only as a **timing gate** (funding must precede first launch) and as a **display statistic** (`launch_count`), never as a qualifying condition for cluster membership itself (membership is edge-connectivity, not launch-count thresholds).

**Direct answer to the brief's three questions**: yes, an operation would still be represented correctly if no subprovider exists (the code path is already exercised — the 2-hop direct case), if no sibling suppression exists (irrelevant to this module by construction), and if creators are funded directly (same as the subprovider case — `treasury_wallet` set with no intermediate hop is exactly what `_find_direct_treasury_for_creator` already handles one layer up in `operational_lineage.py`). **Operation identity is the single most operation-agnostic piece of this whole system** — it is built entirely on "which confirmed treasuries fund which other confirmed treasuries," a concept with no WATCHTOWER-specific shape assumption baked in at all. Its one real limitation is that it requires the root entities to be **confirmed treasuries** specifically (`wt_confirmed_treasuries`) — a different operation family whose root entity isn't called or vetted as a "treasury" would need either reuse of that same confirmation table under a different name, or a parallel resolver; the *mesh-clustering algorithm itself* would transfer unchanged.

## Discovery vocabulary — term by term

| Term | Universal / operation-specific / ambiguous |
|---|---|
| **Fan-out** | Ambiguous, and already flagged as actively misleading in X29.10 — the word itself describes a universal graph-shape concept (one node funding many), but the *implementation* (`_fan_out_count`) reads only Category-C-scoped WATCHTOWER launch tables, so the number displayed under this universal-sounding word is narrower than the word implies even *within* WATCHTOWER, let alone across operation families. |
| **Creator** | Operation-specific by definition — presumes the operation's terminal action is "create a token." Any non-launch operation family has no equivalent, not a renamed one. |
| **Historical launches** | Operation-specific — "launch" is meaningless outside a token-creation context. |
| **Provisioning** | Operation-specific in current usage (`wt_provisioning_edges`, "Provisioning Activity" card) — describes WATCHTOWER's specific treasury→subprov→creator capital-movement pattern; a generic "funding" or "capital flow" vocabulary would be the operation-agnostic equivalent. |
| **Subprovider** | Operation-specific, per the Roles table above. |
| **Treasury** | Borderline universal — "the confirmed root funding entity" is a general concept; the specific term and its confirmation mechanism are WATCHTOWER's, but the underlying idea (a vetted root) generalizes cleanly. |
| **Operation** (the `operation_identity.py` concept itself) | Genuinely universal — "a connected mesh of root funding entities plus their attributed terminal outcomes," as traced above, carries no WATCHTOWER-specific shape assumption. |
| **Funding mechanism tags** (`WSOL_WRAP_CLOSE`/`PLAIN_TRANSFER`/`SEEDED_ACCOUNT_CLOSE`) | Operation-specific by nature (they name concrete on-chain instruction patterns) but architecturally treated correctly — as an open, additive tag set (`MECHANISM_ORDER`, extend by adding a tag, not by restructuring), which is the right shape for a concept that will always be operation/mechanism-specific by definition. |
| **Funding topology tags** (`FAN_OUT`/`LINEAR`/`MESH`/`MULTI_LEVEL_FAN_OUT`) | Universal, per the Topology section above — the shape vocabulary itself generalizes; only the current detectors are WATCHTOWER-table-scoped. |

## Generalisation test — three hypothetical operations

**Example A: Treasury → Creator (2-hop, no subprovider).** Already a real, tested case. `build_lineage()` renders it correctly today (`_find_direct_treasury_for_creator`), `classify_topology_for_launch` returns `LINEAR` (`treasury_direct_no_subprov` branch), and `operation_identity.py` clusters it with no subprov awareness at all. **Fully representable today, no new vocabulary needed.**

**Example B: Treasury → Long-lived distributor → Creator.** This is structurally identical to WATCHTOWER's Subprovider role *if* the distributor is single-hop and its funding is captured in `wt_provisioning_edges`/`wt_watchtower_launches`'s existing columns — `operational_lineage.py` would render it as a `SUBPROVIDER`-role node with a (possibly very large) `fan_out_count`, and nothing would break. But the *label* "Subprovider" would misrepresent a genuinely different operational pattern (a long-lived, reused distribution wallet is a materially different thing from WATCHTOWER's typically single-burst wrap-close subprov, per X29.8/X29.9's finding that ANen's actual behavior — dozens of wallets funded in a single ~7-second burst — is a specific temporal signature, not just "any intermediate funder"). **Representable numerically, but the vocabulary ("Subprovider," "Fan-out") would apply an incorrect WATCHTOWER-flavored narrative onto a distinguishable pattern the architecture currently has no separate name for.**

**Example C: Treasury → Rotating intermediaries → Creator.** This is the case the current architecture is **least equipped to represent faithfully**. `roles_for_wallet()` returns a role per wallet based on static edge participation — it has no concept of a *rotating pool* of intermediaries as a single collective entity distinct from any one member. Each rotating wallet would independently look like its own one-off "Subprovider" with `fan_out_count=1` (exactly X29.10's finding for individual wrap-close intermediaries), and nothing in `operation_identity.py`, `operational_lineage.py`, or `funding_topology.py` currently has a mechanism to recognize "these N wallets are successive rotations of the same functional role" — that would require a new evidence concept (e.g. temporal-sequence or vanity-family linkage, referenced in memory as `vanity-family-attribution` but not wired into any of these three modules). **Not representable today without either new evidence-linkage logic or accepting a fragmented, undercounted picture (N separate one-off "Subprovider" nodes instead of one rotating-distributor concept).**

## Deliverables

**1. WATCHTOWER-specific assumptions currently embedded in Discovery:**
- The Subprovider role's supporting properties (`fan_out_count`, `funding_mechanisms`) are computed only from wrap-close-shaped edge/launch tables.
- CDC and Candidate are WATCHTOWER detection-pipeline staging states, referenced in the brief's role list but not actually roles.
- `MULTI_LEVEL_FAN_OUT`/`MESH` detection reads WATCHTOWER-specific event/session tables (`watchtower_events`, `wt_active_subprov_sessions`) by hardcoded name.
- The mechanism→role promotion rule ("wrap-close observed ⇒ confirmed Subprovider") lives in `ws_cascade.py`'s live detection pipeline, not in any read-only classifier — meaning role assignment itself, not just presentation, is mechanism-coupled for this one case.
- `discovery.html:1271`'s Browse-By-Role panel hardcodes the three-role literal `[{key:'TREASURY'...},{key:'SUBPROVIDER'...},{key:'CREATOR'...}]` — a fixed role list in the UI layer, not derived dynamically from whatever roles actually exist in the data.
- "Creator," "Historical launches," and "Provisioning" are all launch/token-creation-specific vocabulary with no operation-agnostic equivalent currently defined.

**2. Truly operation-agnostic concepts:**
- `operation_identity.py`'s entire mesh-clustering algorithm (confirmed-root funding edges, time-gated, connected-component clustering) — the single strongest example of operation-agnostic design in the codebase.
- `operational_lineage.py`'s variable-depth walk mechanism itself (as opposed to its specific role vocabulary) — the *pattern* of "walk up/down only as far as evidence supports, never pad to a fixed depth" transfers to any operation shape.
- The Fan-Out/Linear/Multi-Level-Fan-Out/Mesh topology vocabulary as *concepts* (their current detectors are not, per above).
- The additive-mechanism-tag pattern in `funding_mechanism.py` (open tag set, never mutually exclusive) — the right shape for something that will always be operation-specific in content.

**3. Roles that should remain optional rather than universal:**
- Subprovider (already effectively optional — the 2-hop direct case proves this) — should be formalized as optional, not merely "sometimes absent."
- Creator (should be understood as "terminal operational outcome," of which token-creation is one instance, not the only possible one).
- CDC and Candidate should not be modeled as roles at all going forward — they are detection-pipeline states that precede role assignment, and conflating them with roles (as the brief's own example list does, by listing them alongside Treasury/Subprovider/Creator) would import a category error into any redesign.

**4. Where funding mechanism and operational role are conflated:**
- One concrete site: `ws_cascade.py:3290-3297`'s CDC→Subprovider promotion on wrap-close observation. This is the only place a mechanism observation directly *becomes* a role assignment rather than being recorded alongside one. Every read-only classifier module (`funding_mechanism.py`, `operational_lineage.py`) correctly avoids repeating this conflation, but none of them can undo it either, since the underlying role data they read was already assigned this way upstream.

**5. Is Discovery presently operation-neutral?**
**No, not yet, but less so than a naive read might suggest.** The core identity-resolution layer (`operation_identity.py`) is genuinely operation-neutral. The lineage-rendering *mechanism* (`build_lineage()`'s variable-depth walk) is operation-neutral in its logic even though its current vocabulary (Treasury/Subprovider/Creator) is WATCHTOWER-flavored. The topology *vocabulary* is operation-neutral even though its *detectors* are WATCHTOWER-table-scoped. The genuinely non-neutral pieces are concentrated in exactly three places: the Subprovider role's WATCHTOWER-specific supporting properties, the hardcoded three-role UI literal in `discovery.html`, and the single mechanism→role promotion rule in `ws_cascade.py`. Discovery today is best described as "an operation-agnostic skeleton (identity, variable-depth lineage, additive mechanism tags, shape-based topology vocabulary) with WATCHTOWER-specific flesh on it (role names, role properties, one hardcoded UI role list, one detection-time mechanism-to-role rule)" — not "WATCHTOWER with different names" at the architectural level, but very much WATCHTOWER-shaped at the vocabulary and UI level.

**6. Can new operation families be added without redefining existing concepts?**
Partially. `operation_identity.py` needs no changes at all — a new operation family using the same confirmed-treasury-mesh concept would cluster correctly today. `operational_lineage.py`'s walk mechanism needs no structural change, but would need new role constants and new `_node_properties()` branches for a family whose intermediate role isn't wrap-close-shaped — additive, not a redefinition, since `ROLE_TREASURY`/`ROLE_CREATOR` are generic enough to potentially be reused (or renamed to something more generic like `ROLE_ROOT`/`ROLE_TERMINAL`) while a new family supplies its own intermediate-role vocabulary. `funding_topology.py` would need new evidence-reading branches (not new topology categories) to detect the same four shapes from a different family's tables. The one place that would require an actual redefinition, not an addition, is `discovery.html:1271`'s hardcoded three-role browse list — that literal would need to become data-driven (derived from whatever roles actually exist for a given operation family) rather than a fixed constant, to avoid silently omitting a new family's roles from the Browse-By-Role page entirely.
